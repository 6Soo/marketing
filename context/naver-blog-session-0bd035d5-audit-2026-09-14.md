## 결론

핵심은 규칙을 몰랐다는 데 있지 않아요. 대상 세션은 새 정본을 읽었다고 보고했고 실제 원고에도 정본 예시를 사용했다고 남겼지만, **예시 문장 교체와 형식 검사만으로 전체 원고 검수를 대신했어요.** 여기에 옛 작업 방식과 도구 장애가 겹쳤어요.

모델 설정이나 캐시 사용량만으로 문체 실패의 원인을 단정하지 않아요. 이번 해결책은 모델 교체나 검수 에이전트 추가가 아니라, 원고의 의미와 전체 흐름을 검증하는 실행 절차예요.

## 문서를 만든 쪽의 보완 책임

- 이전 인계서·보고서·코드에 옛 구조가 남아 있었고, 단일 정본을 새로 만들어도 기존 세션의 작업표까지 자동 교체되지는 않았어요.
- 09-13의 `human-rewrite` 초안은 이 세션에서 제공한 자료였고, 추상적인 해설이 남아 있었어요. 이를 새 원칙으로 쓴 초안이라고 소개한 것은 기준작으로 오해하게 만들 수 있었어요. 그 파일명이나 소개 문구는 품질 통과 증거가 아니에요.
- 기존 정본에는 문체 설명과 교정 예시가 있었지만, 예시의 부분 복사로 전체 검수를 대신하지 못하게 하는 실행 절차가 부족했어요.
- 해결 문서는 `naver-blog/AGENT-WORKFLOW.md`로 분리해요. 문체 규칙을 또 늘리지 않고 읽기·작성·검수·작업 사본 생성·편집·보고 순서를 관리해요.

## 복구 순서

1. 대상 교정 원고는 `draft-needs-rewrite`로 취급해요. 기존 공개 글은 별도의 교정 미완료 상태로 유지해요. 이 감사만으로 발행 여부나 공개 내용이 바뀌었다고 쓰지 않아요.
2. 다음 원고 작업에서는 카페 원문과 사진을 바탕으로 관심과 개요를 새로 잡아요. 09-13·09-14 원고를 완성본으로 복사하지 않아요.
3. 모든 문단에 대해 사실의 연결, 자연스러운 표현, 문단 사이의 연결을 검수해요. 위 표에서 확인한 인과 오류와 중복·추상 해설이 남았으면 검수 완료로 처리하지 않아요.
4. 검수된 MD와 `_stage` 사본을 일치시키고 나서 편집기 작업을 준비해요. 같은 파일과 편집기에 여러 세션이 동시에 쓰지 않아요.
5. 다음 발행 작업 때는 실제 편집기 상태를 새로 읽어요. 기존 내용을 먼저 지우지 말고 복구 자료와 안전한 입력·저장 확인을 확보해요. 타이핑·업로드 장애 원인은 도구의 실제 응답으로 따로 조사해요.
6. 사용자의 발행 요청 범위에서 같은 공개 글을 교정하고, 새 공개 화면을 확인한 뒤에만 완료라고 보고해요.

## 전달 상태와 완료 기준

이 감사 중 파세오의 `send --no-wait`로 대상 세션에 교정 지시를 전달했어요. 모델·작업 모드 변경, 세션 삭제·재시작, 공개 글 수정은 하지 않았어요. 지시는 새 문서 읽기, 옛 형식 강제 중단, 사실 검수, 실패 상태의 정확한 보고, 추가 발행 없이 현재 상태 확인을 요구해요.

명령 전달 성공이나 에이전트의 동의 답변은 행동 교정 완료가 아니에요. 완료 판단은 **다음 원고에서 지적한 문제가 사라지고, 검수 기록이 실제 본문과 일치하며, 발행을 했다면 공개 검증까지 확인되는지**로 해요.
