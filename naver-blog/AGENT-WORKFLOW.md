# 네이버 블로그 에이전트 실행 절차

적용일: 2026-09-14

문체 기준은 `WRITING-RULES.md`, 현재 작업 상태는 루트의 `HANDOFF-NAVER-BLOG.md`가 정본이에요. 이 문서는 규칙을 실제 원고와 행동으로 옮기는 절차예요. 새 문체 공식이나 모델별 검수 조건을 추가하지 않아요.

## 1. 시작할 때 현재 과제를 고정해요

- 최신 사용자 요청이 진단·문서화인지, 원고 작성인지, 발행인지 구분해요. 진단·문서화 요청만으로 편집기나 공개 글을 바꾸지 않아요.
- 루트 `AGENTS.md`, 채널 인계서의 현재 상태, `WRITING-RULES.md`, 이 문서를 읽어요. `CLAUDE.md`가 같은 내용이면 중복 내용을 별도 규칙으로 계산하지 않아요.
- 오래된 채팅의 기억보다 지금 파일의 적용일과 폐기 표시를 확인해요. 옛 보고서·초안·LOG 전체를 선행 로드하거나 거기서 규칙을 다시 뽑지 않아요.
- 내부 작업 메모에 대상 공개 URL, 사용할 원고 파일, 원문과 사진 묶음, 적용 규칙 버전, 이번에 끝낼 범위를 적어요. 파일명에 `human`, `repair`, `approved`가 있어도 내용 검수 증거가 없으면 완료본이 아니에요.
- 규칙이 바뀐 뒤 재개하는 기존 세션은 옛 작업표의 고정 분량·문장 수·모델 검수 조건을 먼저 제거해요. 특정 글에 사용할 사진 목록과 모든 글에 적용하는 사진 수 규칙은 구분해요.

## 2. 브라우저보다 원고를 먼저 완성해요

카페 원문·사진을 다시 보고 글의 관심을 정해요. 옛 원고에 예시 문장만 붙이는 방식으로 새 규칙을 적용했다고 하지 않아요. 전체 구성을 바꾸라는 요청이면 원문 재료에서 새 개요를 만들고, 기존 원고는 확인 자료로만 둬요.

`WRITING-RULES.md`의 예시는 교정 방식을 설명하는 자료이지, 승인된 상용구가 아니에요. 같은 사진에 적합한 표현을 쓰더라도 앞뒤 문장과 중복되는지 다시 확인해요. 교정이 대체인지 삭제인지 추가인지 먼저 결정하고, 바꾼 뒤에는 문단 전체를 다시 읽어요.

### 반드시 분리해서 보는 세 가지 검사

1. **사실과 연결**: 각각 맞는 사실을 거짓 이유로 이어 붙이지 않았는지 확인해요. 예정 출발월은 사진 촬영월·날씨의 근거가 아니고, 항공 경유지는 숙소를 옮기지 않는 이유가 아니에요. `-라서`, `-이니`, `그래서`의 앞뒤가 실제로 원인과 결과인지 봐요.
2. **문장**: 추상적인 해설, 중복 설명, 어색한 구어체, 근거 없는 체험을 찾아 실제 문장을 고쳐요. 글자 수·사진 수·금지어 검사는 문체 검수를 대신하지 못해요.
3. **글 전체**: 예시로 지적된 문단만이 아니라 제목부터 마지막 안내까지 읽어요. 각 문단의 역할, 화제 전환, 감상의 반복, 정보가 끼어드는 위치를 확인해요. 같은 주제를 반복하는 문장은 합치거나 덜어내요.

검수는 `문제 문장 → 문제의 이유와 해당 원칙 → 삭제·이동·재작성 → 수정 뒤 앞뒤 문맥 확인`으로 기록해요. 몇 군데를 고쳤다는 숫자나 `정본 예시 사용`만으로 통과시키지 않아요. 문제가 남으면 원고 상태는 `draft-needs-rewrite`예요.

## 3. 원고 하나를 기준으로 관리해요

- 편집할 MD 하나를 선택하고 내부 기록에 문장 검수 결과와 버전을 남겨요. `_stage/post.txt`는 그 원고에서 만든 작업 사본이며 별도의 정본이 아니에요.
- 문장 검수가 끝난 뒤에만 작업 사본을 갱신하고, 실제 저장 파일을 다시 읽어 본문이 일치하는지 확인해요. 원고가 바뀌면 이전 검수 결과는 새 본문에 자동 승계하지 않아요.
- 같은 원고·작업 사본·편집기는 한 시점에 한 에이전트가 수정해요. 다른 세션의 변경이나 예상과 다른 파일 내용을 발견하면 먼저 다시 읽고 원인을 확인해요. 낡은 메모리의 내용으로 덮어쓰지 않아요.
- 원문에 없는 내용을 문장 개선이라는 이유로 보태지 않아요. 회사 자산 승인 등 이미 확인된 사실은 새 반증이 없으면 재승인을 반복 요구하지 않아요.

## 4. 원고 상태와 발행 상태를 섞지 않아요

| 상태 | 필요한 증거 |
|---|---|
| `draft-needs-rewrite` | 미해결 문장 문제와 재작성할 파일이 명시됨 |
| `copy-reviewed` | 최종 본문 버전, 사실·문장·전체 흐름 검수 기록이 일치함 |
| `editor-partial` | 실제 입력된 부분과 남은 부분을 새 화면에서 확인함 |
| `published-unverified` | 공개 동작은 했지만 새 공개 본문을 검증하지 못함 |
| `published-verified` | 공개 URL에서 제목·전체 본문·사진·링크를 검증하고 결과를 기록함 |

기존 공개 글과 교정 작업의 상태는 따로 적어요. `교정본 미발행`을 `기존 글도 미발행`으로 바꾸지 않아요. 작업표의 완료 표시도 이 증거를 따라요. 실패를 정리했다는 이유로 발행 항목에 완료 표시를 하지 않아요.

## 5. 도구 장애가 나도 원고 기준을 바꾸지 않아요

- 도구가 사진과 글의 수를 같게 요구한다면 도구의 입력 제약이에요. 글을 그 제약에 억지로 맞추거나 폐기된 문체 규칙을 되살리지 않아요. 현행 일일 발행 스크립트의 옛 입력 구조는 별도 개선 대상이에요.
- 빈 자동 발행 큐는 예약 실행에 처리할 항목이 없다는 뜻이에요. 사용자가 특정 글 발행을 요청했을 때 새 원고 준비와 검수를 시작하지 못하는 이유는 아니에요. 그렇다고 검수 결과나 큐의 승인 값을 꾸며 넣어서는 안 돼요.
- 현재 제공된 브라우저 도구의 문서와 지원 기능 안에서 작업해요. 편집기 내부 객체 변경, 합성 이벤트, 화면 DOM 변경을 실제 저장 성공으로 간주하지 않아요.
- 기존 제목·본문·사진을 지우기 전에 복구 자료와 현재 상태를 남겨요. 안전한 임시 초안에서 입력·저장·다시 읽기가 되는지 확인하지 못했다면 기존 글을 먼저 비우지 않아요.
- 실패하면 도구명, 대상, 시각, 기대한 결과, 실제 반환값과 화면 변화를 기록해요. 같은 실패를 새 가설 없이 반복하지 않아요. 범위를 좁힌 확인에서도 진전이 없으면 편집을 멈추고 현재 상태를 보존해요.
- 리소스 목록에 요청이 보이지 않는다는 이유만으로 서버·계정 차단을 배제하거나 확정하지 않아요. 도구 응답·관찰 범위·네트워크 근거가 부족하면 원인 미확정이라고 써요.
- 도구 장애를 이유로 업로드·붙여넣기·발행 전체를 사용자에게 기본 인계하지 않아요. 확인 가능한 진단과 안전한 대안을 먼저 제시해요. 사용자 개입은 로그인·이차 인증·캡차·권한 복구처럼 실제 필요한 최소 동작으로 한정하고, 수동 마무리는 사용자가 선택한 경우에만 안내해요. 불가능한 자동화를 가능하다고 약속하지도 않아요.

## 6. 재개 요청을 받았을 때의 최소 보고

규칙을 길게 복창하지 말고 다음 네 가지를 보여줘요.

- 지금 적용할 규칙 파일과 사용할 원고
- 해당 원고에서 발견한 구체적인 문제
- 이번에 수행한 수정과 검증 결과
- 아직 끝나지 않은 단계와 실제 장애 근거

출력 예시는 품질 보증이 아니에요. 에이전트가 새 절차를 읽었다는 답변도 실행 완료가 아니에요. 다음 원고와 검수 기록에서 실제로 문제가 사라졌는지 확인해야 해요.
