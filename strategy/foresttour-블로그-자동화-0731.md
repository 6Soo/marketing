## 결론

foresttour.kr 블로그는 Instagram의 **발견 이후 역할**을 자사 사이트 안에서 완결하고,
검색·RSS·직접 링크라는 독립 발견 경로를 만듭니다. 그러나 Instagram 추천 알고리즘의 초기 대량
도달과 사회적 반응까지 같다고 주장하지 않습니다. 목표는 채널 폐기가 아니라
**Instagram이 멈춰도 콘텐츠 자산과 전환 동선이 멈추지 않는 상태**입니다.

## 자동화 설계

공개 원고는 `blog/published/stories.json` 하나로 관리합니다. 카드뉴스 시리즈와 사실 검증 문서에서
초안 골격을 만들 수 있지만, 자동 생성은 빈 본문·사진 권리·공식 출처·상품 연결을 완성한 척하지
않습니다. 사람이 검수한 초안만 명시적 `--publish`로 공개본에 승격합니다.

foresttour.kr은 GitHub main의 공개 원고를 1시간 단위로 읽습니다. 원격 데이터가 HTTPS·크기·
스키마·사진·일정 연결 계약을 통과하지 못하면 마지막 정상 번들로 폴백합니다. 이 구조로 새 글은
마케팅 리포 한 곳만 바꾸면 되고, 원격 원고 장애가 사이트 장애로 번지지 않습니다.

긴급 삭제는 예외입니다. 원격에서만 글을 지우면 장애 시 번들이 되살릴 수 있으므로 마케팅 공개본과
앱 번들에서 함께 제거하고 앱을 재배포한 뒤 404·목록·RSS·sitemap 제거를 확인합니다. 폴백 발동은
Vercel 로그에 경고를 남깁니다.

자동 커밋 봇은 두지 않습니다. 앱 리포는 예약 개인정보를 다루므로 공개 콘텐츠 자동화가 PII
저장소의 git 작업 권한을 갖는 것보다, 런타임 읽기 전용 결합과 마지막 정상 스냅샷이 안전합니다.

## 발견·검색 표면

- `/stories`와 고유 `/stories/<slug>` canonical
- Blog·BlogPosting JSON-LD와 공개/수정일
- 고유 Open Graph 이미지
- XML sitemap과 RSS 2.0
- robots.txt의 절대 sitemap URL
- 홈과 목록의 내부 링크

Google은 sitemap을 발견을 돕는 힌트로 설명하며 색인을 보장하지 않습니다. RSS/Atom도 sitemap으로
제출할 수 있습니다. Article 구조화 데이터 역시 적격성을 높이지만 리치 결과를 보장하지 않으므로,
완료 판정은 “색인 보장”이 아니라 **크롤링 가능성·정합성·실제 검색 노출의 후속 관측**으로 나눕니다.

- <https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap>

1. 여행지 기록 목록 방문
2. 목록 또는 홈에서 글 선택
3. 글 착륙
4. 본문 맥락 도달
5. 관련 글 선택

Google·네이버·다음·Bing 자연검색을 Instagram과 분리합니다. 검색 브라우저가 referrer를
제거하면 `direct`로 남기며, 존재하지 않는 정밀도를 만들기 위해 추정하지 않습니다. 전체 referrer
URL은 서버에 보내지 않고 브라우저에서 채널 코드로 축약하므로 경로·쿼리를 저장하지 않습니다.

  - 채택: 목표를 “Instagram 의존 제거”로 한정하고 도달 역할은 상호 보완으로 기록했습니다.
